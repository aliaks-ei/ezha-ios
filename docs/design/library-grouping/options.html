Library grouping and search

Four options for the Library tab and for the Library picker on the Log meal screen. Each phone works: type in search, switch the filter, tap rows, tap the letter index. Use the toggle above each phone to switch between the Library tab and the Log meal picker.

Recommendation

Option D (hybrid). Show “Usual now”, Favorites and Recent on top, then all items A–Z with a letter index. Rank search results by match quality, then by use. Build it in two steps:

  1. Step 1, no backend change: Favorites + Recent on top, A–Z sections with sectionIndexLabel, ranked search with typo tolerance, “Estimate with AI” when nothing matches.
  2. Step 2, small backend change: count uses per time of day, then add the “Usual now” section.

Skip AI categories (Option C) for now. People look for a saved item by name or by habit, not by food type. AI labels add cost, need a backfill, and a wrong label hides the item.

What the research says

  • Habit beats browsing. MyFitnessPal shows the right foods for the current meal at the top, so no search is needed. Cronometer users complain that recent foods show up “hit or miss”. Cronometer forum, MacroFactor vs Cronometer.
  • Time of day and consistency rank suggestions. Carbon suggests a food at the meal where you usually log it, and lists the most consistent habits first. It waits for 7 active logging days. Carbon help.
  • Speed is counted in actions. MacroFactor measures loggers by the number of taps per log. Fewer taps per item matters more than smart ranking. MacroFactor FLSI.
  • Alphabetical order is for known names. Nielsen: alphabetical sorting rarely helps, except when users know the exact name. A–Z is a good fallback for the long tail, not a good first screen. Cardinal Path on Nielsen.
  • Frecency (frequency + recency) is the standard ranking for “items I use”. Raycast useFrecencySorting.
  • Native letter index exists on iOS 26. Section { … }.sectionIndexLabel("A") and .listSectionIndexVisibility(.visible) on the List. The app targets iOS 26.0, so no custom scrubber is needed. Apple docs, Hacking with Swift.

A. Alphabet sections with a letter index

Contacts pattern

How it works

  1. Favorites stay pinned on top.
  2. All other items sit in letter sections A–Z.
  3. The letter index on the right edge jumps to a section.
  4. Search shows one flat list, ranked by match quality.

Good

  • No backend change. Native API: sectionIndexLabel.
  • Predictable. The item is always in the same place.

Weak

  • Daily items are not on the first screen. Oatmeal sits under O every morning.
  • Useful only after about 30 items. Short libraries get many one-item sections.

B. Usage sections

MyFitnessPal and Carbon pattern

How it works

  1. “Usual now”: up to 5 items you often log at this time of day. Change the time above to see it change.
  2. “Favorites”, then “Recent” (last 7 days, not already shown).
  3. “Everything else”: most used first.
  4. Each item shows once, in the first section that fits.

Good

  • The usual item is one tap away, with no search.
  • Works best in the Log meal picker, where speed matters most.

Weak

  • New users have no history. “Usual now” stays hidden until about 7 logging days.
  • The tail is hard to scan: no order a person can predict.

Data needed

  • log_food_entry already sets last_used_at for p_used_food_ids. Add use_count and three slot counters (morning, midday, evening) to saved_foods, and increase them in the same update.
  • The client must send the local hour, because the server does not know the user’s time zone.

C. AI categories

AI groups

How it works

  1. AI gives each item one category when you save it: Breakfast, Protein, Dairy and eggs, Grains, Fruit and veg, Snacks, Drinks, Sauces.
  2. Saved meals stay in their own “Meals” group.
  3. Chips at the top filter to one category. The count shows group size.
  4. Inside a group, most used first.

Good

  • Helps browse: “what snacks do I have?”.
  • Groups stay stable, unlike usage sections.

Weak

  • One AI call per save, plus a backfill for existing items.
  • A wrong or unexpected label hides the item (is “Protein bar” a Snack or Protein?). Needs a manual override in the editor.
  • Does not make daily repeats faster.

D. Hybrid Recommended

Habit first, A–Z after

How it works

  1. Top: “Usual now” (step 2), Favorites, Recent. Each item shows once.
  2. Below: “All items” in A–Z sections. The A–Z list contains every item, so the letter index always works.
  3. The letter index starts with ★ to jump back to the top.
  4. The Foods / Meals filter still applies to all sections. Favorites moves out of the filter and into a section.
  5. Search ranks: name starts with the term, then a word starts with it, then it contains it, then a one-letter typo. Ties go to the most used.
  6. No match in the picker: one row “Estimate ‘…’ with AI” sends the text to the logger.

Why this one

  • Daily items are one tap away. Rare items are found by name or letter.
  • Step 1 ships with no backend change and fixes most of the pain.
  • Same layout in the Library tab and in the picker, so users learn it once.

Build order

  1. LibraryFilter: add sections(...) that returns pinned + A–Z sections, and rank(...) for search. Add tests next to LibraryFilterTests.
  2. LibraryView and LibraryPickerView: render sections, add sectionIndexLabel, flat ranked list while searching.
  3. Picker: “Estimate with AI” row when search has no match.
  4. Step 2: migration for use counters, update log_food_entry, add “Usual now”.

Search rules for all options

  1. While the user types, drop the sections and show one ranked list. Groups slow down scanning when the user already knows the name.
  2. Rank by match quality first, then by use. Today the app keeps the default order and only filters.
  3. Allow one wrong letter in terms of 5+ letters (“chiken” finds “Chicken”).
  4. Highlight the matched text.
  5. Keep the current filter (Foods / Meals) while searching.
