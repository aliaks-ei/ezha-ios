Meal review: three layout options

Each option lets you check and change grams, per-100 g values and portion macros without leaving the review, and shows how the meal changes today's balance before you log it. The phone mockups are interactive: type in the grams and per-100 g fields, use the steppers and tap the rows.

What slows the user down now

  1. The review shows grams and calories only. Protein, carbs and fat for a food are not shown anywhere.
  2. Per-100 g values are never shown, not even for a scanned label.
  3. To change grams: tap the pencil, open “Edit portion”, type, tap Done, go back. Four steps for each food.
  4. You can only edit macros for a label, and only as a meal total on the “Nutrition details” screen, two levels down.
  5. The review does not show the effect on today's target. You must log the meal and go back to Today to see it.
  6. “Scan label” is hidden in the “…” menu, and a photo of a label needs a separate “Nutrition label” switch.

What every option must do

  1. Show calories, protein, carbs and fat for each food on the review screen, with no navigation.
  2. Let the user type grams directly. The numbers update while they type.
  3. Show per-100 g and portion values side by side. Per-100 g values are editable, so the user can correct them from the label.
  4. Show today after this meal: calories left and each macro left or over, live.
  5. Keep one primary action, “Log meal”, with the meal total on it.

Show the three ways in with the same weight

  1. Show “Photo of food”, “Scan label” and “Saved foods” as three tiles. Scan label leaves the “…” menu.
  2. Keep the text field below the tiles, with a Photos button inside it.
  3. “Scan label” sets the label mode itself. Remove the “Nutrition label” switch.
  4. After a label scan, the review opens with the grams field focused and the label's per-100 g values shown. The user types how much they ate and logs.
  5. A photo or label goes to estimation right away. The user does not tap “Estimate nutrition” when there is no text to add.

Item 5 changes the current flow, where the user can add text to a photo before the estimate. Keep a short delay with a “Add details” link if you want to keep that.

Option A: Expandable food rows My pick

A calm list. Each row shows macros and an editable grams field. Tap a row to open the per-100 g table in place. The balance panel sits above Log meal.

Tap a row to expand. Type in any field.
How it works
  1. Each food is one row: name, calories, protein, carbs and fat in grams, and a grams field.
  2. Tap the grams field and type. The row, the meal total and the balance panel update while you type.
  3. Tap the row to expand it. It shows a table with two columns: “Per 100 g” (editable) and “This portion”.
  4. The expanded row also has ±10 g buttons, the optional Raw / Cooked question, and Remove.
  5. The panel above Log meal shows today after this meal: calories left and each macro left or over. The striped part of each bar is this meal.
Good
  • Grams and macros: no taps to see, one tap to change. Per-100 g: one tap.
  • The default view stays calm. Detail shows only for the food you open.
  • The balance panel is next to Log meal, where the user decides.
  • Native parts: list rows, Grid, TextField with .decimalPad, the existing bottom safeAreaInset.
Watch
  • The panel is about 150 pt tall. On a compact iPhone, collapse it to one line (“254 kcal left · Protein 6 g over”) that expands on tap.
  • Keep only one row open at a time, so the list does not get long.
  • Add a keyboard toolbar with Previous, Next and Done to move between fields.

Option B: Nutrition table for each food

Every number is visible at all times. Each food is a card with a per-100 g row and a portion row. The balance strip stays at the top while you scroll.

Use the steppers or type in the per-100 g row.
How it works
  1. The balance strip at the top shows calories, protein, carbs and fat left after this meal. It stays in place while you scroll.
  2. Each food card has a grams stepper in the header.
  3. Under it is a table: the “100 g” row is editable, the portion row is calculated.
  4. The meal total is under the last card and on the Log meal button.
Good
  • No taps to see any number. This is the fastest way to compare a result with a label.
  • Easy to compare foods, because the columns line up.
Watch
  • Dense. Most meals do not need per-100 g values every time.
  • Five columns do not fit at large text sizes. At accessibility sizes, each card must change to stacked rows.
  • Three foods already scroll on a standard iPhone.

Option C: Balance header and an edit sheet

The day's balance is the main element. Foods are compact rows. Tap a food to edit it in a half-height sheet, and the balance above stays visible and updates live.

The sheet is open on Chicken breast. Tap Done, then tap any row.
How it works
  1. The header shows the calorie ring and three macro bars. The striped part is this meal.
  2. The list shows each food: grams, calories and macros.
  3. Tap a food to open a sheet at half height: large grams field, −/+ buttons, quick amounts, and a “Per 100 g / This portion” switch with editable values.
  4. The header stays visible above the sheet and changes while you edit.
Good
  • Best answer to “does this meal fit my day?”.
  • Large touch targets. Works well at large text sizes.
  • Native: .presentationDetents([.medium, .large]) with .presentationBackgroundInteraction(.enabled(upThrough: .medium)).
Watch
  • One more tap than A to see per-100 g values or to change grams.
  • The user must close the sheet to change to a different food.
  • A sheet on top of the logger sheet adds one level of depth.

Recommendation: Option A

A puts the numbers most users need (grams and macros) in the list, and keeps per-100 g values one tap away. The balance panel next to Log meal answers “does this fit my day?” at the moment of decision. It also keeps the current calm look and native list parts. If you check labels on most meals, B is the better choice.

Rules for all options

  1. Saved meals (macroBasis = .perOriginal) have no per-100 g values. Show a “Per serving (X g)” column for them.
  2. A changed per-100 g value marks the food as “Edited”. A new AI estimate must not overwrite it without a warning.
  3. The balance uses the target of the logger's date, not today, when the user logs a past day.
  4. Calories do not recalculate from protein, carbs and fat. Each value is stored as entered.
  5. Log meal stays blocked for invalid grams, as now (AnalyzeGate.logBlockReason).

Decisions for you

  1. Which option: A, B or C?
  2. Allow editing per-100 g values for AI estimates, or only for label and saved foods?
  3. Send a photo to estimation right away, or keep the step to add text first?
